## Remaining findings

### S1 — P1: A concurrent catalog update can still lose its referenced file

**Reproduced; residual of R6.** [delete_service.py:259](/Users/nawdddep/Downloads/all-set-mac-app-main/scripts/cloud/delete_service.py:259) checks for shared references after deleting the source row, then permanently removes held files at line 266. Those separate operations do not coordinate with a catalog writer.

Probe: A referenced `live/aaaa.mp4`; B initially referenced nothing. The probe wrapped `key_used_elsewhere` to insert a real Postgres update immediately after the second reference check returned false, representing a concurrent writer. B then referenced `live/aaaa.mp4`. Delete A returned **200**, reported the file removed, left B's key intact, and removed the file. The DB update, delete and filesystem cleanup were real; the wrapper controlled their interleaving.

The ordinary already-shared-file case is repaired. The broader concurrent-write guarantee is not. Use a coordination protocol followed by both deletion and catalog writers, with recoverable asset retirement. Merely adding another reference check leaves another race window; a database transaction alone cannot cover the filesystem or uncoordinated writers.

### S2 — P2: Cancellation has weaker guarantees than timeout, and descendants can survive

**Reproduced.** [CommandRunner.swift:89](/Users/nawdddep/Downloads/all-set-mac-app-main/Sources/AllSetCore/Support/CommandRunner.swift:89) only sends termination on task cancellation. The no-timeout path waits indefinitely at line 65; cancellation does not activate the timeout path's SIGKILL escalation.

Probe: a disposable Python command ignored SIGTERM and naturally exited after three seconds. Cancelling after its readiness signal returned only after **3.04 seconds**, with “python3 was cancelled.” A non-terminating command would keep waiting. The existing cancellation test uses `sleep`, which obeys termination, so it misses this case.

A second probe ran a shell waiting for a Python child that ignored SIGTERM. After a 0.5-second timeout, the runner reported “sh took too long and was stopped”, but the child was still alive. The probe explicitly killed that child afterward. The timeout implementation targets the tracked process for SIGKILL, without guaranteeing its descendants have stopped. Descendants holding stderr can also keep the background drain worker blocked after the caller returns.

Give cancellation the same bounded stop/escalation policy as timeout and define process-group/descendant ownership for user shell commands. Verify TERM-ignoring cancellation and descendants, not just commands that cooperate.

### S3 — P2: The new containment helper leaks a realpath allocation on every successful search

**Reproduced with allocation instrumentation.** [ContainedPath.swift:31](/Users/nawdddep/Downloads/all-set-mac-app-main/Sources/AllSetCore/Support/ContainedPath.swift:31) calls `realpath(path, nil)` as a Boolean condition. On success, libc allocates a buffer, and that result is discarded. The second call at line 35 allocates another buffer; only that second buffer is freed.

An isolated executable compiled the current helper with wrappers forwarding `realpath`/`free` to Darwin and counting their returned/released pointers. **1,000 containment checks made 4,000 allocations and freed 2,000**, leaving 2,000 outstanding allocations. The probe freed those outstanding buffers before exiting. This establishes the leak; no claim is made about its measured effect on application RSS.

Retain and free the successful search result, or supply caller-owned storage. The containment checks themselves now reject the earlier escaping paths; this is a resource regression introduced by the repair.

### S4 — P2: Screenshot request invalidation does not stop obsolete work

**Source-backed; original wrong-document bug is repaired.** [ScreenshotStudio.swift:113](/Users/nawdddep/Downloads/all-set-mac-app-main/Sources/AllSetCore/AI/ScreenshotStudio.swift:113) invalidates replies by generation but owns no cancellable request task. Replacing a screenshot resets `isWorking`, allowing another request while the old one continues retaining its image/session and using the provider.

There is also no generation check between detached Claude image preparation and sending the request at [line 153](/Users/nawdddep/Downloads/all-set-mac-app-main/Sources/AllSetCore/AI/ScreenshotStudio.swift:153). Replacing the document during preparation can still submit obsolete work afterward. Closing the retained studio window has no cancellation or image-release hook in the controller.

Own the task at the document/controller boundary, cancel on replacement, check generation before submission, and define an explicit close/clear policy. Cancellation cannot guarantee a provider has not already processed a submitted request, but it can stop preventable preparation/submission and release local work.

The 600 MB history limit is also a **soft retained-pixel budget**, not a total memory ceiling: [line 79](/Users/nawdddep/Downloads/all-set-mac-app-main/Sources/AllSetCore/AI/ScreenshotStudio.swift:79) stops eviction with two states left; original/current images, sessions and concurrent work can exceed it. Ordinary history growth is improved, but oversized imports and overlapping requests still need resource limits.

## Product and release gaps still open

- **UI/UX:** The earlier navigation fragmentation and oversized utility-page presentation remain. This pass found no redesign in their repair status. Those earlier visual observations were not freshly rerun here.
- **Privacy:** [ClipboardSettings](/Users/nawdddep/Downloads/all-set-mac-app-main/Sources/AllSetCore/Clipboard/ClipboardStore.swift:104) still enables collection by default, keeps 200 unpinned items and defaults clear-on-quit to false. Pending-capture invalidation is repaired; the first-run collection/retention decision remains open.
- **Storage/recovery:** No coherent user-data export/restore format, downloaded-photo disk quota, server backup or rehearsed restore. Hash-checking before offload does not make the server a backed-up storage system.
- **Backend operations:** Delete/catalog services remain manually started. Versioned migrations, coordinated catalog/deletion writes and catalog pagination remain absent. These are acceptable constraints for a personal deployment, but they must shape the product's promises.
- **Release confidence:** Real-app workspace restoration, identical monitors, minimum supported macOS, permission revocation and VoiceOver remain unverified. Developer ID signing/notarization, update/rollback and clean-machine installation remain open. An ad-hoc signature verification is not distribution readiness.

## Recommended order

1. Coordinate server deletion with catalog writes and add the interleaving regression.
2. Fix bounded cancellation/descendant cleanup and the containment allocation leak.
3. Own screenshot request lifetimes and apply input/resource limits.
4. Resolve clipboard onboarding/retention and simplify navigation.
5. Complete backup/restore and packaged-release/platform validation before widening distribution.
