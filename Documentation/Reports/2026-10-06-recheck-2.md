## Remaining actionable findings

### T1 — P1: Expiry sweeping can permanently remove a newly referenced retired file

**Reproduced with real disposable Postgres and storage.** [delete_service.py:317](/Users/nawdddep/Downloads/all-set-mac-app-main/scripts/cloud/delete_service.py:317) obtains a reference snapshot, then [line 328](/Users/nawdddep/Downloads/all-set-mac-app-main/scripts/cloud/delete_service.py:328) permanently removes expired files from that snapshot. The sweep does not hold the database's asset lock across the check and filesystem decision. `BUSY` serializes local sweeps/deletes but does not coordinate catalog writers.

Probe: create a retirement batch dated eight days ago, containing `live/aaaa.mp4`, and a row B with no playback key. Wrap `referenced_keys` so that, immediately after its real query reports no references, a real Postgres transaction takes the documented asset advisory lock and sets B's playback key to `live/aaaa.mp4`. Resume the actual sweep. Result:

```
Sweep result: ([], ['live/aaaa.mp4'])
Surviving row key: live/aaaa.mp4
Retired original survives: False
Live copy exists: False
```

The wrapper controls the interleaving; reference lookup, locked DB update and file removal are real. This writer takes the lock but does not validate that the live file exists, matching the late/manual-reference recovery scenario the new service explicitly attempts to support. This is not proof that a writer obeying both the lock and live-file existence rules loses an existing live copy.

Seven-day retirement closes the previous immediate-loss window but moves a remaining permanent-loss boundary to expiry. The repair register should not call the broader race fully fixed. Coordinate final purge with supported writers, enforce the live-file reference rule in the actual uploader, and state the limits for manual/uncoordinated updates. Add a regression for a reference committed between the expiry check and removal. A transaction covering only the earlier row delete does not protect this later boundary.
