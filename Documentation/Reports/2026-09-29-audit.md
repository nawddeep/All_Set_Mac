## Top 10 findings

### 1. Active wallpaper never recovers after a failed fetch (server down / Tailscale late at login) — P1, confirmed bug
- Evidence: `Sources/AllSet/Wallpaper/WallpaperController.swift:402` — fetch task id is
  `"\(id)#\(hasLoadedLibrary)"`; both are constant after load. A thrown fetch
  (`WallpaperStore.swift:306` `fetch(relative:)`) is swallowed with `try?`; nothing re-keys the task.
- Root cause: `.task(id:)` only reruns when its id changes. No retry, and `serverReachable` isn't part of the id.
- Reproduce: offload the active wallpaper, turn Tailscale off, relaunch → default art. Turn Tailscale on → stays on art until relaunch or a wallpaper change. At login Tailscale commonly connects after the app starts, so this hits the first fetch of every boot.
- Fix: retry with capped backoff inside the task while the view exists (e.g. 2 s → 60 s, cancelled with the view), or include a reachability generation counter in the id, bumped by a periodic `checkServerReachable`.
- Regression risk: low; must keep the `hasLoadedLibrary` part of the id (race fix).
- Test: Y — store-level: first fetch fails (stub 500), second succeeds after handler flips; assert a retry helper eventually returns the file.

### 2. Re-importing a source folder after offload undoes it or strips `playback` — P1, confirmed by reading the importer
- Evidence: `scripts/wallpaper_library.py:1367` (`output_ok` requires the local playback file → scene re-rendered); `:1575-1590` (plain video: if `originals/<id>` is missing, `playback` is only set when `--self-contained`, which re-copies from the drive; without it the entry loses `playback` entirely).
- Root cause: the importer treats "not on this Mac" as "never made"; it predates offloading.
- Reproduce: after Free Up Space, run `import <folder>` for a source folder: hours of re-rendering + ~20–50 GB re-copied, or (without `--self-contained`) offloaded plain videos lose `playback` and can no longer be fetched (the app needs `playback` to build the server path).
- Fix: importer keeps a cached result/`playback` when the file is absent locally but was recorded as offloaded (e.g. an `offloaded` marker the app writes, or a HEAD check against the server before re-rendering).
- Regression risk: medium (touches the idempotency logic, R6).
- Test: Y — Python-side: entry with `playback` missing locally + offloaded marker survives an import unchanged.

### 3. Free Up Space deletes the active wallpaper, which is then immediately re-downloaded — P2, measured
- Evidence: `WallpaperStore.swift:363` `offloadCandidates` doesn't exclude `config.source`. After the full run `extracted/` was 0 B; minutes later it held only `aa58634b7be43e2c.mp4` (69 MB) = the active wallpaper, fetched back.
- Root cause: deliberate choice ("never touches config.source"), but the next redraw re-fetches it at once.
- Fix: skip the active `.library(id)` in `offloadCandidates` (report it as kept, "in use").
- Regression risk: low. Test: Y — active id is kept, others freed.

### 4. Thumbnail tile stays blank if scrolled away and back during its fetch — P2, confirmed by reading (latent: thumbnails are currently kept local)
- Evidence: `WallpaperPages.swift:588` `try? await store.fetchThumbnail(...)`; `WallpaperStore.swift:308` throws `alreadyFetching` for the second task; `LibraryTile` doesn't observe `fetches`, so nothing reloads it when the first download lands.
- Fix: on `alreadyFetching`, await the in-flight fetch (store a `Task` per relative path and return its value) instead of throwing.
- Regression risk: low. Test: Y — two concurrent `fetchThumbnail` calls both return the file.

### 5. Downloads outlive their views and aren't cancellable — P2, confirmed
- Evidence: `WallpaperStore.swift:314` continuation has no `withTaskCancellationHandler`; the URLSession task keeps running when the SwiftUI task is cancelled.
- Impact: switching quickly through offloaded wallpapers downloads every one of them in full (each up to ~750 MB for `originals/`).
- Fix: `withTaskCancellationHandler { … } onCancel: { task.cancel() }` — but only cancel when no other caller waits (ties in with #4).
- Regression risk: medium (must not cancel a fetch another view is waiting on). Test: Y — cancel mid-download leaves no file and no `fetches` entry.

### 6. DEBUG library probe now has side effects on real data — P2, confirmed by reading
- Evidence: `Sources/AllSet/Widgets/PageCPUProbe.swift:542` sets synthetic entries (real `playback` paths) as the active wallpaper; with files offloaded this triggers real server downloads into the real library, and `store.config = quiet` persists to `wallpaper.json` during the run.
- Fix: probe sets `libraryServerURL = nil` in its quiet config and restores it; or use a temp directory store.
- Regression risk: none for users (DEBUG only). Test: N.

### 7. System wallpaper (lock screen / Mission Control) isn't refreshed after a fetch lands — P2, confirmed (known issue 4)
- Evidence: `WallpaperController.swift:223-224, 269` — `stillImage(for:)` returns nil while the file is missing, `appliedSystemSource` is reset, and `sync()` only reruns on config/screen changes.
- Fix: observe `libraryCopies`/fetch completion for the active id and call `matchSystemWallpaper` again.
- Regression risk: low. Test: N (AppKit-level); manual.

### 8. Any fetch progress redraws every `WallpaperView` at 4 Hz — P2, suspected (not profiled)
- Evidence: `WallpaperStore.swift:298` `let underway = fetches` reads the whole dictionary, so each wallpaper window + the hero preview depends on every fetch (thumbnails included), updated every 250 ms.
- Fix: read only `fetches[relative]` (Observation tracks the dictionary property as a whole either way — so better: a per-relative-path observable or a coarser "fetch finished" counter).
- Regression risk: medium — this read is what makes a finished fetch redraw the view (race fix #2 of the last checkpoint). Measure with Time Profiler first.
- Test: N.

### 9. `reloadLibrary()` on every page appear can drop a just-fetched copy from `libraryCopies` — P3, suspected race
- Evidence: `WallpaperPages.swift:205` `.onAppear { store.reloadLibrary() }`; `WallpaperStore.swift:177` rebuilds `libraryCopies` from a disk snapshot taken before a concurrent fetch lands, then assigns over the fetch's `insert`.
- Impact: tile shows "Fetch from Server" for a file that is local, until the next reload. Playback unaffected (`libraryURL` checks disk).
- Fix: recompute membership for ids with an in-flight fetch after it finishes, or merge instead of assign.
- Test: Y — reload during a stubbed slow fetch keeps the id.

### 10. Free Up Space scan and delete loop run on the main thread — P3, measured
- Evidence: `WallpaperPages.swift:429` `offloadableSpace()` (48 ms debug for 282 local files; ~2× for a fully local library), `WallpaperStore.swift:413` deletes up to ~1500 files synchronously on the main actor.
- Fix: do the stat scan and unlinking in a detached task, hop back to update `libraryCopies`.
- Regression risk: low. Test: N.

## Suspicious code paths / possible races (not top 10)
- `offloadAll` has no re-entrancy guard; two concurrent runs would share `offloadProgress` (`WallpaperStore.swift:386,407`). The UI hides the button while running, so only reachable programmatically.
- `fetch(relative:)` does `removeItem` then `moveItem` (`WallpaperStore.swift:314+`), not an atomic replace; harmless today because the destination never exists.
- Server verification is status + `Content-Length` only (the invariant). A same-size corrupt server file would pass; stronger options: compare sha256 via a sidecar manifest on the server.
- `checkServerReachable` runs only when the Library page appears; `serverReachable` can stay `true` for hours after the server goes down (banner/button state stale; deletion safety unaffected — it re-checks every file).
- ATS exception is by IP (`Resources/Info.plist`); switching `libraryServerURL` to the Tailscale hostname silently breaks every fetch (offload stays safe: it keeps everything).
- Each test's `WallpaperStore` creates a URLSession that's never invalidated (tests only).
- `deleteLibraryVideo` rewrites `catalog.json` with `.sortedKeys`: semantics and importer fields preserved (tested), formatting differs from the importer's.
- The importer and the app can both write `catalog.json`; last writer wins. Deletions stay correct because the importer re-reads `removed.json` late, but other app-side catalog edits (none today) would be lost.

## Known issues — classification
1. Full-library offload not yet run — **stale**: it was run (commit `b07714a`, 18.7 GiB freed). 280 `originals/` files were correctly kept because they weren't on the server; their push is in progress.
2. Offloaded wallpapers need Tailscale + server — **architectural limit** (made worse by finding 1: no recovery once they're back).
3. Hover previews don't fetch offloaded wallpapers — **intentional** (avoids downloading on every hover); could become a future feature with a delay + size cap.
4. System wallpaper doesn't refresh after fetch — **bug** (finding 7).
5. ~700 older wallpapers lack crossfade fix / blank check — **architectural limit** (needs source data or a re-render path from local copies; after offload, from the server).
6. `libraryServerURL` has no settings UI — **future feature**.
7. SSH key has no passphrase — **intentional** (unattended sync); security trade-off, not a bug.
8. User-deleted wallpapers stay on server — **intentional**.
